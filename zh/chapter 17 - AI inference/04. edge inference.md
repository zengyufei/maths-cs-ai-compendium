# 边缘推理

*边缘推理在用户设备，手机、笔记本和 IoT 传感器上运行模型，不将数据发送至云端。本节涵盖边缘约束、模型压缩流水线、设备端运行时、编译器栈、硬件目标，NPU 和神经引擎、设备端 LLM、联邦学习及延迟优化。*

- 云端推理依赖网络连接，会增加延迟，往返 50 至 200 ms，每个请求产生费用，并将用户数据发送到第三方服务器。**边缘推理**消除了这四项：模型在本地运行，立即响应，每次推理没有额外成本，数据也保持私密。

- 代价是边缘设备的计算和内存仅为数据中心 GPU 的 $100$ 至 $1000$ 分之一。让模型在这些约束内运行，需要在每个层面进行激进优化。

!!! note "大白话"
    边缘推理把延迟、隐私和联网成本降到最低，但设备不可能像数据中心一样堆显卡。能否运行，取决于模型、运行时和硬件是否一起为这台设备做了取舍。

- **Cactus**（[github.com/cactus-compute/cactus](https://github.com/cactus-compute/cactus)）是专为移动和可穿戴设备构建的低延迟 AI 引擎。它在生产环境中展示了本节的许多技术：用于注意力和矩阵运算的自定义 ARM SIMD 内核，第 16 章，KV-cache 量化，第 17 章第 01 节，分块 prefill，Apple 与 Qualcomm 芯片上的 NPU 加速推理，零拷贝内存映射以将 RAM 使用量降低 10 倍，以及设备端算力不足时自动回退到云端。Cactus 在 iOS、Android、macOS 和嵌入式 Linux 上支持多模态推理，LLM、视觉和语音，并提供 Swift、Kotlin、Python、Flutter、React Native 和 Rust SDK。其基准显示，INT4 的 1.2B 模型在 M4 Pro 上解码速度为 100 tokens/s、在 iPhone 17 Pro 上为 48 tokens/s，这是优化边缘推理的具体实例。

!!! note "大白话"
    真正可用的边缘引擎不会只靠一种技巧，而是把低比特、SIMD、NPU、内存映射和云端回退组合起来。设备性能不够时要优雅降级，不能让用户只看到卡死或失败。

## 边缘约束

| 资源 | 云端 GPU（H100） | 笔记本（M4） | 手机（Snapdragon 8 Gen 3） | IoT（ESP32） |
|----------|-----------------|-------------|---------------------------|-------------|
| RAM | 80 GB HBM3 | 16-36 GB unified | 8-12 GB LPDDR5 | 520 KB |
| 计算 | 989 TFLOPS（FP8） | 38 TOPS（Neural Engine） | 45 TOPS（NPU） | 0.001 TOPS |
| 功耗 | 700 W | 15-30 W | 5-10 W | 0.1 W |
| 存储 | TB | 256 GB-2 TB | 128-512 GB | 4 MB |

- 云端 GPU 与手机 NPU 的算力差距约为 20 倍；GPU 与微控制器之间约为 1,000,000 倍。不同设备需要不同程度的压缩和不同模型架构。

!!! note "大白话"
    “在设备上跑”不是一个统一难度：笔记本能跑数十亿参数模型，手机通常要更小更低比特，微控制器只能跑极小网络。部署前先看内存、带宽和功耗，不要只看 TOPS 宣传数字。

## 模型压缩流水线

- 对边缘部署而言，压缩不是单一技术，而是一条按顺序应用互补技术的**流水线**：

```
Full model (FP32, 70B params)
    ↓ Knowledge distillation → smaller model (7B params)
    ↓ Structured pruning → remove redundant heads/layers (4B effective)
    ↓ Quantisation (INT4) → 4x smaller (2 GB)
    ↓ Compiler optimisation → fused kernels, optimised memory layout
    ↓ Runtime → on-device execution
```

- 每一步都缩小尺寸并降低延迟，顺序也很重要：先蒸馏，缩减架构；再剪枝，移除结构；再量化，降低精度；最后编译，为目标硬件优化。量化后再蒸馏，等于尝试压缩已产生损失的模型。

!!! note "大白话"
    压缩流水线像先把箱子里的东西减少，再整理结构，最后把每件东西装得更紧。顺序错了会在已经损失精度的模型上继续操作，通常更难保住质量。

## 设备端运行时

- **运行时**加载模型、分配内存并在目标硬件上执行推理。每个平台都有偏好的运行时：

- **ONNX Runtime**：跨平台，Windows、Linux、macOS、iOS、Android。支持 CPU、GPU，CUDA、DirectML、CoreML、NNAPI，及众多加速器后端，是可移植性最高的选择。模型从 PyTorch 或 TensorFlow 导出为 ONNX 格式。

- **TensorFlow Lite（TFLite）**：Google 的边缘运行时，为 ARM CPU 和 Android NPU 优化。二进制文件极小，约 1 MB，支持 INT8 和 float16，是 Android 部署的标准选择。

- **Core ML**：Apple 面向 iOS/macOS 的运行时，会依模型特征自动使用 Neural Engine、GPU 或 CPU。模型通过 `coremltools` 从 PyTorch 或 TensorFlow 转换，与 Apple 硬件，统一内存、Neural Engine，紧密集成。

- **ExecuTorch**：Meta 面向设备端 PyTorch 的新运行时。它以提前编译为边缘部署设计，并可将算子级工作委派给硬件加速器，是 PyTorch Mobile 的继任者。

- **TensorRT**：NVIDIA 的 GPU 推理优化运行时，第 15 章。它融合层、选择最佳内核并自动量化，在 NVIDIA GPU 上比 PyTorch eager mode 快 2 至 5 倍。

- **llama.cpp**：面向 LLM 的单文件 C++ 推理引擎。支持 GGUF 量化，Q4、Q5、Q8，CPU，AVX/NEON，Metal，Apple GPU，CUDA 和 Vulkan，是在消费级硬件上运行 LLM 的首选。

!!! note "大白话"
    运行时决定模型到底怎么落到设备上。跨平台优先 ONNX Runtime，Android 常用 TFLite，Apple 用 Core ML，NVIDIA 用 TensorRT，本地 LLM 常用 llama.cpp；选错运行时，模型再小也可能用不上硬件加速。

## 编译器栈

- 高层模型，PyTorch 图，和硬件，NPU 指令，之间是**编译器栈**，它为特定目标优化模型：

```
PyTorch model
    ↓ Export (torch.export, ONNX, TorchScript)
Graph IR (intermediate representation)
    ↓ Graph optimisations
        - Constant folding (compute constant expressions at compile time)
        - Dead code elimination (remove unused operations)
        - Operator fusion (conv + bn + relu → single fused op)
        - Layout transformation (NCHW → NHWC for ARM, channels-last)
    ↓ Lowering
Hardware-specific IR
    ↓ Backend optimisations
        - Tiling and loop ordering (cache-friendly access patterns)
        - Vectorisation (SIMD, chapter 16)
        - Memory planning (reuse buffers to minimise peak memory)
        - Kernel selection (choose the best implementation per op)
    ↓ Code generation
Machine code / NPU instructions
```

- **算子融合**是影响最大的优化。一个 transformer block 有约 20 个操作，矩阵乘、加法、layernorm、softmax 等。没有融合时，每个操作都将输出写入内存，下一操作再读回；融合后，多个操作组合为单个内核，数据保留在寄存器或缓存中。这可快 2 至 5 倍，第 16 章 roofline model。

!!! note "大白话"
    层与层之间的中间张量不是免费产生的，每次写回 RAM 再读出都很慢。融合把连续步骤合在一次内核里完成，尤其适合带宽有限的手机和 IoT 设备。

- **内存规划**：编译器分析模型图，判断哪些 tensor 的存活期重叠，并让它们共享同一内存缓冲区。一个模型有 100 个中间 tensor 时，可能只需要其中 10 个的内存，因为多数 tensor 会在其他 tensor 创建前被消费和释放。这对 RAM 有限的设备至关重要。

!!! note "大白话"
    编译器不只是把 Python 翻译成机器码，还会合并算子、重排数据布局、复用临时缓冲区。边缘设备 RAM 很小，少存一次中间结果常常比单个算子快一点更重要。

## 硬件目标

### 移动 GPU

- **Qualcomm Adreno**，Android：支持 OpenCL、Vulkan compute，第 16 章，以及 Qualcomm 专有的 SNPE，Snapdragon Neural Processing Engine。Adreno GPU 有 256 至 1024 个 ALU，支持 FP16 和 INT8。

- **ARM Mali**，Android：支持 OpenCL 和 Vulkan。Mali GPU 使用基于 tile 的架构，与桌面 GPU 不同，会影响最佳内存访问模式。

- **Apple GPU**，iOS/macOS：通过 Metal，Apple 的 GPU API，访问。统一内存架构意味着没有 CPU↔GPU 拷贝开销。Metal Performance Shaders，MPS，提供优化的 ML 基元。

!!! note "大白话"
    移动 GPU 的 API 和内存结构差别很大，不能照搬桌面 CUDA 假设。Apple 统一内存少一次复制，Android 设备则更依赖 Vulkan、厂商驱动和具体芯片能力。

### 神经处理单元（NPU）

- NPU 是专门为 ML 推理设计的固定功能加速器。对于标准 ML 运算，矩阵乘、卷积、激活函数，它们比 GPU 节能得多。

- **Apple Neural Engine**：16 核，约 38 TOPS，INT8。通过 Core ML 访问，特别适合视觉模型和设备端扩散模型。它不能运行任意代码，只能运行 Core ML 支持的操作。

- **Qualcomm Hexagon NPU**：集成在 Snapdragon SoC 中，支持 INT8 和 INT4 推理。通过 SNPE 或带 QNN 后端的 ONNX Runtime 访问，为背景虚化、语音识别和实时翻译等设备端功能提供动力。

- **Google Edge TPU**：云 TPU 的小型低功耗版本，4 TOPS、2W，用于 Coral 设备上的设备端推理，只支持 INT8 量化的 TFLite 模型。

!!! note "大白话"
    NPU 用专用电路把标准 ML 算子做得很省电，但支持范围有限。例如 Edge TPU 只吃 INT8 TFLite；模型中有不支持算子，就可能回退到慢 CPU 路径。

- **委派模式**：运行时在 NPU，支持的操作，和 CPU，不支持的操作，之间拆分模型图。尽可能提高在 NPU 上运行的比例，是性能和能效的关键。

!!! note "大白话"
    NPU 对常见矩阵和卷积非常省电，但不会执行任何算子。模型一旦频繁在 NPU、GPU、CPU 之间切换，数据搬运会吃掉收益，所以要尽量让连续的大段图留在同一加速器。

## 设备端 LLM

- 小模型与激进量化使在手机和笔记本上运行 LLM 成为现实：

| 模型 | 参数量 | 量化后大小 | 目标设备 | 性能 |
|-------|--------|---------------|---------------|-------------|
| Phi-3 Mini | 3.8B | ~2 GB（Q4） | 手机/笔记本 | iPhone 15 上约 15 tokens/s |
| Gemma 2B | 2B | ~1.5 GB（Q4） | 手机 | Pixel 8 上约 20 tokens/s |
| Llama 3.2 1B | 1B | ~700 MB（Q4） | 手机 | ~30 tokens/s |
| Llama 3.2 3B | 3B | ~2 GB（Q4） | 手机/笔记本 | ~15 tokens/s |
| Llama 3.1 8B | 8B | ~4.5 GB（Q4） | 笔记本 | M2 上约 20 tokens/s |

- **挑战**：
    - **内存**：3B Q4 模型能装入 2 GB，但长对话的 KV-cache 会显著增加占用。手机上的上下文长度通常限制在 2-4K token。
    - **热降频**：持续推理会使手机发热。连续生成 30 秒后，SoC 为防过热而降低时钟频率，性能下降 30 至 50%。
    - **电池**：以 15 tokens/s 运行 3B 模型消耗约 3-5W；30 分钟对话耗尽典型手机约 5% 的电量。偶尔使用可接受，常驻应用则有问题。

!!! note "大白话"
    手机上的模型大小只是第一关。上下文越长缓存越大，持续生成会触发热降频，还会明显耗电，所以实际体验必须按持续时长而不是刚启动时的峰值 token/s 来设计。

- **llama.cpp** 是设备端 LLM 的标准。它运行在 CPU，AVX2、NEON、I8MM，Apple GPU，Metal，NVIDIA GPU，CUDA，AMD GPU，ROCm/Vulkan，甚至手机，Android 上经 Termux，之上。

!!! note "大白话"
    设备端 LLM 的难题不只是权重能不能装下：长对话的 KV-cache 会继续增长，持续生成还会让手机过热、耗电。实际产品要限制上下文、控制生成时长，并准备性能下降后的体验。

## 联邦学习

- **联邦学习**在许多设备间训练模型，而不集中数据。每个设备在本地数据上训练、计算梯度更新，只向中心服务器发送更新，不发送数据；服务器聚合更新。

- **算法**，FedAvg：
    1. 服务器将当前模型发送至选定的 $K$ 个设备。
    2. 每个设备在本地数据上对模型微调若干步。
    3. 每个设备将更新后的模型，或差分，发送回服务器。
    4. 服务器平均这些更新：$W_{\text{new}} = \frac{1}{K} \sum_{k=1}^{K} W_k$。
    5. 重复。

!!! note "大白话"
    FedAvg 的流程是服务器发模型，设备各自在本地学一点，再把更新平均。数据不集中，但设备的网络、算力和数据分布都不一致，训练会比数据中心更难协调。

- **隐私**：原始数据永不离开设备，服务器只看到聚合后的模型更新。**差分隐私**向更新加入噪声，使单个数据点无法从梯度中反向推断。

- **通信效率**：模型更新很大，与模型本身相同大小。压缩技术可缓解：**梯度量化**，发送 INT8 梯度而不是 FP32，**稀疏化**，仅发送最大的梯度，以及**梯度累积**，在本地执行更多步、降低发送频率。

!!! note "大白话"
    联邦学习把数据留在设备上，只上传模型更新，因此隐私更好；但更新本身也可能很大，还可能泄露信息。实际系统需要同时做加密、差分隐私和通信压缩，不能把“数据没上传”当成绝对安全。

- **应用**：Google 键盘预测，Gboard，Apple 语音识别、健康监测，在不集中敏感健康数据的情况下训练。

!!! note "大白话"
    联邦学习提高隐私的前提是原始数据不上传，但模型更新仍可能泄露特征。需要差分隐私、安全聚合和更新压缩一起配合，才能在隐私、准确率和流量之间取得平衡。

## 延迟优化

- 除压缩外，还有多项技术可降低端到端推理延迟：

- **早退出**：在中间层添加分类头。若模型在第 6 层，满共 24 层，已足够自信，则不运行第 7 至 24 层，直接返回预测。简单输入早退出，困难输入使用完整模型。对于难易混合的任务，平均延迟显著下降。

- **模型切分**：将模型拆分到 NPU，高效执行矩阵乘，GPU，高效执行不规则操作，和 CPU，处理其他操作。编译器依据 profiling 决定每个操作的位置。

- **缓存**：对于重复查询的应用，自动补全、代码补全，缓存近期计算。当用户输入 “我该如何”，而模型最近已为 “我该如何” 生成补全时，可复用缓存的 KV-cache，完全跳过预填充（prefill）阶段。

- **推测预取**：预测用户下一步操作，在用户提出请求前开始推理。聊天应用可在用户阅读当前回答时，开始生成可能的后续问题的回答。

!!! note "大白话"
    早退出、切分到不同芯片、缓存和预取都在减少用户真正等待的时间。预取猜错会白耗电和算力，所以只能用在下一步高度可预测的场景。

## 编程任务（使用 CoLab 或 notebook）

1. 模拟模型压缩流水线。从 float32 模型开始，应用蒸馏，模拟、剪枝和量化，并跟踪每一步的大小。
```python
def compression_pipeline(original_params_M, original_bits=32):
    size_mb = original_params_M * 1e6 * original_bits / 8 / 1e6

    print(f"Original: {original_params_M}M params, {original_bits}-bit → {size_mb:.0f} MB")

    # Step 1: Knowledge distillation (reduce params)
    distilled_params = original_params_M * 0.15  # 70B → ~10B equivalent
    size_mb = distilled_params * 1e6 * original_bits / 8 / 1e6
    print(f"After distillation ({distilled_params:.0f}M params): {size_mb:.0f} MB")

    # Step 2: Structured pruning (remove 30% of remaining)
    pruned_params = distilled_params * 0.7
    size_mb = pruned_params * 1e6 * original_bits / 8 / 1e6
    print(f"After pruning ({pruned_params:.0f}M params): {size_mb:.0f} MB")

    # Step 3: INT4 quantisation
    size_mb = pruned_params * 1e6 * 4 / 8 / 1e6
    print(f"After INT4 quantisation: {size_mb:.0f} MB")

    print(f"Total compression: {original_params_M * 1e6 * original_bits / 8 / 1e6 / size_mb:.0f}x")

print("=== Starting from 70B model ===")
compression_pipeline(70000)

print("\n=== Starting from 7B model ===")
compression_pipeline(7000)
```

2. 估计设备端推理延迟。给定模型操作数和硬件规格，计算其是否达到延迟目标。
```python
def estimate_latency(model_name, params_M, bits, compute_tops, mem_bw_gbs, seq_len=256):
    """Estimate token generation latency for a memory-bandwidth-bound model."""
    # Model size in bytes
    model_bytes = params_M * 1e6 * bits / 8

    # Decode is memory-bound: must load entire model per token
    time_per_token_ms = model_bytes / (mem_bw_gbs * 1e9) * 1000

    # Tokens per second
    tokens_per_sec = 1000 / time_per_token_ms

    print(f"{model_name}: {params_M/1000:.1f}B params @ {bits}-bit = {model_bytes/1e9:.1f} GB")
    print(f"  Memory bandwidth: {mem_bw_gbs} GB/s")
    print(f"  Time per token: {time_per_token_ms:.1f} ms")
    print(f"  Tokens/sec: {tokens_per_sec:.0f}")
    print()

# Apple M2 Pro: 200 GB/s unified memory bandwidth
print("=== Apple M2 Pro (200 GB/s) ===")
estimate_latency("Llama-7B Q4", 7000, 4, 15.8, 200)
estimate_latency("Llama-7B Q8", 7000, 8, 15.8, 200)
estimate_latency("Llama-70B Q4", 70000, 4, 15.8, 200)

# Phone (Snapdragon 8 Gen 3): ~50 GB/s LPDDR5
print("=== Snapdragon 8 Gen 3 (50 GB/s) ===")
estimate_latency("Phi-3 Mini Q4", 3800, 4, 45, 50)
estimate_latency("Llama-3B Q4", 3000, 4, 45, 50)
```
