# 扩展与部署

*要向数百万用户提供大模型，需要将推理分布到多张 GPU、在 token 被需要前预测它们、缓存共享上下文，并选择合适框架。本节涵盖推理并行、推测解码、前缀缓存、推理框架、成本优化和监控。*

- 一张为 70B 模型提供交互式低延迟服务的 H100 GPU 可处理约 100 名并发用户。服务 1,000 万用户需要 100,000 张 GPU，每年云计算成本约 $30 亿。效率每提升一个百分点，就可节省数千万美元。因此推理优化并非学术问题，它直接决定 AI 产品的经济性。

!!! note "大白话"
    单次推理省几毫秒，在大规模服务里会被放大成大量 GPU 和电费。推理优化的目标不是跑一个漂亮基准，而是用更少硬件稳定服务更多真实用户。

## 推理时的模型并行

- 当模型大到单张 GPU 放不下时，必须拆分到多张 GPU。训练中的并行策略，第 6 章，也可用于推理，但取舍不同。

### 张量并行

- **张量并行**，Megatron 风格，第 6 章，将单个权重矩阵拆分到 GPU。对于线性层 $Y = XW$，权重矩阵 $W$ 在 $N$ 张 GPU 上按列拆分。每张 GPU 计算部分结果，然后通过 all-reduce 聚合：

$$W = [W_1 | W_2 | \cdots | W_N], \quad Y_i = X W_i, \quad Y = \text{concat}(Y_1, \ldots, Y_N)$$

- 推理时，张量并行是模型无法放入单张 GPU 时的默认选择。FP16 的 70B 模型需要 140 GB，可用张量并行拆分至 $2 \times 80$ GB GPU。

!!! note "大白话"
    张量并行的第一目标是把太大的单层权重拆开装进去。它在高速 NVLink 机器内效果最好，若只是 PCIe 拼卡，通信延迟会很快变成用户可感知的等待。

- **延迟影响**：张量并行每层增加一次 all-reduce 通信。在 NVLink，900 GB/s，上，每层约增加 0.1 ms；在 PCIe，32 GB/s，上，每层约增加 3 ms。对于 2 张 GPU 上的 80 层 70B 模型，NVLink 总共增加约 8 ms，PCIe 增加约 240 ms。这正是 NVLink 对多 GPU 推理极其重要的原因。

!!! note "大白话"
    张量并行是把同一层拆给多张 GPU 同时算，能解决“模型塞不下”的问题，但每层都要交换结果。GPU 间带宽不够时，通信会把计算省下来的时间全吃掉。

### 流水线并行

- **流水线并行**将不同层分配给不同 GPU。GPU 1 处理第 0-39 层，GPU 2 处理第 40-79 层，token 顺序流经流水线。

- 推理时，流水线并行比张量并行有更高延迟，每个 token 必须遍历整个流水线，却有更低通信开销，只在 GPU 之间传递 activation，不需要 all-reduce。当 GPU 通过慢速互连连接，不同节点、没有 NVLink，时更适用。

!!! note "大白话"
    流水线并行让不同 GPU 负责不同层，像产品按工序传递。单个 token 要经过所有工位，所以交互延迟较高，但跨机器只传激活值，适合 GPU 之间网络较慢的情况。

### 序列并行

- 对很长的序列，即使模型本身能放下，KV-cache 也可能放不进单张 GPU。**序列并行**将 KV-cache 分片到多张 GPU：每张 GPU 保存部分序列的缓存键和值。

- 注意力计算时，每张 GPU 在其缓存片段上计算部分注意力分数，再由归约合并结果。它用于 128K+ token 的长上下文推理，此时 KV-cache 超出单张 GPU 的内存。

!!! note "大白话"
    序列并行不是拆模型权重，而是拆超长上下文的 KV-cache。它让每张卡只保留一段历史，换取跨卡合并注意力结果的通信成本。

## 推测解码

- **推测解码**是影响最大的 LLM 推理优化之一。其洞见是：解码慢，因为它一次生成一个 token，每个 token 都需要大模型完整前向传播。但小模型可更快生成候选 token，大模型可并行**验证**多个候选。

![推测解码：快速草稿模型生成 5 个候选 token，目标模型一次前向传播验证全部；接受通过候选并重采样被拒绝候选](../images/speculative_decoding.svg)

- **算法**：
    1. **草稿模型**，小且快，例如 1B 参数，自回归生成 $k$ 个候选 token。
    2. **目标模型**，大且准确，例如 70B，在整个草稿序列上执行一次前向传播，计算每个候选 token 的概率。
    3. 若目标模型同意，目标模型为该 token 分配的概率足够高，则**接受**候选；被拒绝候选从目标模型分布重采样。
    4. 平均而言，每次验证接受多个 token，速度提升与接受率成正比。

!!! note "大白话"
    推测解码的收益取决于草稿模型和目标模型有多像，以及草稿有多便宜。草稿总猜错时只会多做工作；接受率高时，目标模型一次验证就能替代多次 decode。

$$\text{Speedup} \approx \frac{k \times \text{acceptance\_rate}}{\text{cost\_ratio}} \approx 2\text{-}3\times$$

- **为何没有质量损失**：拒绝采样方案保证输出分布与目标模型完全一致。推测解码无损，输出在统计上与单独运行目标模型相同，只是更快。

!!! note "大白话"
    草稿模型负责大胆猜几步，目标模型仍负责最终裁决。猜对越多，一次昂贵前向传播就能确认多个 token；猜错时回退重采样，因此不会把草稿模型的错误直接交给用户。

- **变体**：
    - **Medusa**（Cai 等，2024）：不使用独立草稿模型，而是为目标模型添加多个轻量“head”，同时预测多个未来 token，无需独立模型。
    - **EAGLE**（Li 等，2024）：训练轻量草稿 head，使用目标模型的隐藏状态预测未来 token，比独立草稿模型有更高接受率。
    - **自推测解码**：目标模型自身通过早退出产生草稿，只运行前几层，然后使用完整模型验证。
    - **并行解码**：并行生成多个延续，候选树，并一次验证整棵树。吞吐量更高，但分支 KV-cache 占用更多内存。

## 前缀缓存

- 许多请求共享共同前缀：系统提示词、few-shot 示例或常见查询模式。**前缀缓存**保存这些前缀的 KV-cache，并跨请求复用。

- **系统提示词缓存**：若每个请求都以相同的 2000-token 系统提示词开始，则这 2000 个 token 的 KV-cache 只计算一次，供全部请求共享。对于 80 层 70B 模型，每个请求可节省约 200 MB。

- **基数树缓存**，SGLang：在基数树，trie，中组织缓存前缀。新请求到达时，找到最长已缓存前缀匹配，从此处开始生成，跳过匹配前缀的计算。

!!! note "大白话"
    基数树缓存把许多相似前缀组织成共享分支，不是只缓存一个完整提示词。新请求越像已有请求，就越能从中间位置接着算，省下更多 prefill。

- **影响**：对于有长共享前缀的应用，具有系统提示词的聊天机器人、含共同检索段落的 RAG，前缀缓存将 TTFT 降低 50 至 90%，并按比例节省 GPU 计算。

!!! note "大白话"
    很多请求开头其实完全相同，例如系统提示词和固定规则。前缀缓存把这一段预填充结果复用掉，用户不是从零开始等模型重新读同样的内容。

## KV-cache 驱逐

- 除量化 KV-cache，第 01 节，及使用 GQA/MLA 缩小其大小，第 02 节，外，**KV-cache 驱逐**策略会选择性删除未来不太可能被关注的缓存 token。

- **H2O**，Heavy-Hitter Oracle，Zhang 等，2023，发现注意力分数遵循幂律：少量 token，“heavy hitter”，获得大部分注意力，多数 token 获得的注意力可忽略。H2O 保留：

    1. **最近 token**，最后 $w$ 个 token 的滑动窗口，类似 StreamingLLM。
    2. **重头 token**，过去所有 decode 步的累计注意力分数最高的 top-$k$ token。

- 既非最近 token 也非重头 token 的项被驱逐。这样能保持固定大小 KV-cache，同时保留真正影响生成的 token。H2O 仅用 20% 内存便得到接近完整 KV-cache 的质量。

- **Scissorhands**（Liu 等，2023）采用相似方法，但使用更复杂的重要性度量：当前步收到高注意力的 token 被保留，而连续 $T$ 步未被关注的 token 被驱逐。这会适应生成过程中变化的注意力模式。

!!! note "大白话"
    H2O 看长期累计最重要的 token，Scissorhands 还会观察当前生成阶段的关注变化。两者都在用注意力分数预测哪些历史值得占显存，而不是机械地只保留最新内容。

- **动态驱逐 + StreamingLLM**：将 attention sink，永久保留最前的几个 token，和动态驱逐，保留最近 token 加重头 token，结合。这是很长生成最节省内存的方法，能以有界的质量下降实现无限长度生成。

- 所有驱逐方法的关键洞见：实践中的 LLM 注意力是**稀疏的**。尽管架构对所有缓存 token 计算注意力，实际权重集中在小子集上，驱逐其余 token 对输出质量影响很小。

!!! note "大白话"
    KV-cache 驱逐是在有限内存里保留“最近的”和“最常被关注的”，放弃长期不重要的历史。它能让缓存大小封顶，但会带来可控的质量风险，不能用于必须逐字记住全部上下文的任务。

## 推理框架

- LLM 服务生态已收敛出几种主流框架：

| 框架 | 优势 | 最适用场景 |
|-----------|-----------|----------|
| **vLLM** | PagedAttention、连续批处理、高吞吐量 | 通用 LLM 服务、最高吞吐量 |
| **TensorRT-LLM** | NVIDIA 优化内核、FP8、in-flight batching | NVIDIA GPU 上的最高性能 |
| **SGLang** | 前缀缓存，RadixAttention，快速结构化生成 | 共享前缀、受约束输出的应用 |
| **llama.cpp** | CPU/Metal/CUDA/Vulkan、GGUF 量化、可移植 | 消费级硬件、设备端推理 |
| **TGI**，HuggingFace | 简洁 API、易部署、模型库集成 | 快速部署、HuggingFace 生态 |
| **Ollama** | 一条命令下载并提供模型服务 | 个人使用、本地开发 |
| **ExLlamaV2** | 极致量化优化，EXL2 格式 | 内存受限的 GPU 推理 |

- **vLLM** 是生产 LLM 服务的默认选择。它支持连续批处理、PagedAttention、张量并行、推测解码、LoRA 服务及大部分开源模型。

- **TensorRT-LLM** 在 NVIDIA 硬件上具有最高原始性能，同一 GPU 上比 vLLM 快 10 至 30%，但灵活性更低，也更难定制。

!!! note "大白话"
    框架选择也是控制权和效率的交换。越贴近 NVIDIA 专用内核，峰值可能越高；越通用和易改，往往要放弃一部分极限性能。

- **SGLang** 依靠基数注意力缓存和受约束解码引擎，在结构化输出，JSON、指定格式的代码，或共享前缀的应用中表现突出。

!!! note "大白话"
    推理框架没有万能第一名：vLLM 偏通用吞吐量，TensorRT-LLM 偏 NVIDIA 极致性能，SGLang 强在共享前缀和结构化输出，llama.cpp 强在本地可移植。按工作负载选，不要只看排行榜。

## 成本优化

- 在大规模场景，推理成本占据 ML 预算的主导。降低成本的策略：

- **恰当选择 GPU**：并非每个模型都需要 H100。量化 7B 模型可在 A10G，约 $1/小时，良好运行，而 H100 约 $8/小时。让 GPU 与工作负载匹配。

- **竞价实例**：云服务商对未使用 GPU 容量提供 60 至 90% 折扣，AWS Spot、GCP Preemptible。竞价实例可能被中断，因而适合批量推理而非延迟关键的服务。结合抢占处理，保存状态并在新实例恢复，竞价实例也能服务交互流量。

- **自动扩缩容**：按流量增减 GPU 数量。高峰时扩容，夜间缩容。Kubernetes HPA，Horizontal Pod Autoscaler，或云原生自动扩缩容，AWS SageMaker、GCP Vertex AI，可处理这项工作。

!!! note "大白话"
    竞价实例省钱但会被收回，自动扩缩容能随流量调整容量，两者都需要可恢复的服务状态。没有排队、健康检查和预热策略，省下的 GPU 费用会变成服务抖动。

- **批处理与利用率**：30% 和 90% GPU 利用率之间，是每 token 成本 3 倍的差异。连续批处理、智能调度和 PagedAttention 都会提升利用率。

- **量化**：INT4 比 FP16 内存少 4 倍，可装入更小 GPU，成本降低 2 至 4 倍；同时同一 batch 可容纳更多请求，吞吐量更高，每 token 成本更低。

!!! note "大白话"
    成本优化先让模型和 GPU 匹配，再提高利用率，最后才考虑便宜但会中断的竞价实例。把大模型硬塞进最贵 GPU、却只用到 30%，通常是最浪费的部署方式。

- **每百万 token 成本基准**，约值，2026：

| 配置 | 每 1M token 成本 |
|-------|-------------------|
| GPT-4o API | $2.50 |
| Claude 3.5 Sonnet API | $3.00 |
| H100 上的 Llama-70B，vLLM、FP16 | $0.50 |
| H100 上的 Llama-70B，TRT-LLM、INT8 | $0.25 |
| A10G 上的 Llama-8B，vLLM、INT4 | $0.05 |
| 设备端 Llama-3B，llama.cpp | $0，硬件已摊销 |

!!! note "大白话"
    每百万 token 成本把模型大小、精度、GPU 单价和利用率折算成一个能比较的业务数字。设备端不是完全免费，只是硬件成本已由用户设备承担，仍要考虑电池和体验成本。

## 监控

- 生产推理需要持续监控，在用户受影响前发现退化：

- **延迟监控**：跟踪 TTFT 和 TPOT 的 p50、p95、p99。p99 超过 SLO 时告警。p99 激增通常意味着：KV-cache 内存压力，抖动，长期请求独占 batch，或 GPU 热降频。

- **吞吐量监控**：跟踪每张 GPU 的 tokens/s。下降意味着：batch 效率降低，许多短请求导致 batch 利用率低，序列长度增加，每个请求占用更多 KV-cache 内存，或硬件问题，GPU 处于 ECC 纠错模式、运行较慢。

- **GPU 利用率**：跟踪 SM 占用率、内存利用率和内存带宽。低 SM 占用率加高内存利用率表示受内存限制，需要更高带宽或量化；高 SM 占用率加低内存利用率表示受计算限制，需要更多 FLOPS 或更小模型。

!!! note "大白话"
    指标要组合起来读：GPU 利用率低可能是没请求，也可能是内存卡住；吞吐量低也可能是长上下文吃掉了缓存。监控不是收集一堆数，而是定位下一步该扩容、量化还是修复回归。

- **模型质量监控**：跟踪逐请求指标，响应长度、保留集上的困惑度、用户反馈信号。模型质量可能因数据漂移，传入请求的分布改变，长对话中 KV-cache 量化误差累积，或服务流水线 bug 而下降。

- **成本监控**：按模型、GPU 类型跟踪每 token 成本。若成本增加而吞吐量未增加，检查效率回归：新模型版本使用更多内存、batch 配置不佳或 GPU 未充分利用。

- **工具**：Prometheus + Grafana，第 15 章，用于基础设施指标；vLLM/TRT-LLM 内建指标端点；以及模型级指标的自定义日志。

!!! note "大白话"
    线上不能只盯平均速度。p99 变差、KV-cache 压力、GPU 利用率异常和模型质量下降，都会先伤到少量用户再扩散；监控要同时覆盖延迟、吞吐量、成本和质量。

## 编程任务（使用 CoLab 或 notebook）

1. 模拟推测解码。使用快速“草稿”函数和慢速“目标”函数，测量一次生成并验证多个 token 的加速效果。
```python
import random
import time

def target_model(tokens):
    """Slow but accurate model. Returns probability of each candidate token."""
    time.sleep(0.01)  # simulate 10ms per forward pass
    # For simulation: accept tokens that are even numbers
    return [0.9 if t % 2 == 0 else 0.1 for t in tokens]

def draft_model():
    """Fast but approximate model. Generates one candidate token."""
    time.sleep(0.001)  # simulate 1ms per token
    return random.randint(0, 9)

def standard_decoding(n_tokens):
    """Generate one token at a time with the target model."""
    tokens = []
    for _ in range(n_tokens):
        time.sleep(0.01)  # target model generates 1 token
        tokens.append(random.randint(0, 9))
    return tokens

def speculative_decoding(n_tokens, k=4):
    """Generate k draft tokens, verify with target, accept/reject."""
    tokens = []
    total_target_calls = 0

    while len(tokens) < n_tokens:
        # Draft: generate k candidates quickly
        candidates = [draft_model() for _ in range(k)]

        # Verify: one target model call for all k candidates
        probs = target_model(candidates)
        total_target_calls += 1

        # Accept tokens until one is rejected
        for i, (tok, prob) in enumerate(zip(candidates, probs)):
            if random.random() < prob:
                tokens.append(tok)
                if len(tokens) >= n_tokens:
                    break
            else:
                # Resample from target distribution
                tokens.append(tok + 1)  # simplified resampling
                break

    return tokens, total_target_calls

n = 50

start = time.time()
_ = standard_decoding(n)
standard_time = time.time() - start

start = time.time()
_, target_calls = speculative_decoding(n, k=5)
spec_time = time.time() - start

print(f"Standard:    {standard_time:.2f}s ({n} target calls)")
print(f"Speculative: {spec_time:.2f}s ({target_calls} target calls)")
print(f"Speedup:     {standard_time / spec_time:.1f}x")
```

2. 估计对 LLM 服务部署应用不同优化策略后的成本节省。
```python
def serving_cost_analysis(
    model_name, params_B, precision_bits,
    gpu_name, gpu_mem_gb, gpu_cost_per_hr,
    target_throughput_tps,
):
    """Estimate serving cost for an LLM deployment."""
    model_size_gb = params_B * 1e9 * precision_bits / 8 / 1e9
    gpus_for_model = max(1, int((model_size_gb * 1.2) / gpu_mem_gb + 0.99))  # 1.2x for KV-cache

    # Rough throughput estimate (memory-bandwidth limited)
    tokens_per_gpu = 500 / (params_B * precision_bits / 16)  # normalised to 500 tok/s for 7B FP16
    total_throughput = tokens_per_gpu * gpus_for_model

    replicas = max(1, int(target_throughput_tps / total_throughput + 0.99))
    total_gpus = gpus_for_model * replicas
    cost_per_hr = total_gpus * gpu_cost_per_hr
    cost_per_1M_tokens = cost_per_hr / (total_throughput * replicas * 3600 / 1e6)

    print(f"{model_name} @ {precision_bits}-bit on {gpu_name}:")
    print(f"  Model size: {model_size_gb:.0f} GB → {gpus_for_model} GPU(s)/replica")
    print(f"  Throughput: {total_throughput:.0f} tok/s/replica")
    print(f"  Replicas for {target_throughput_tps} tok/s: {replicas}")
    print(f"  Total GPUs: {total_gpus}")
    print(f"  Cost: ${cost_per_hr:.0f}/hr, ${cost_per_1M_tokens:.2f}/1M tokens")
    print()

print("=== Cost Comparison ===\n")

# Baseline: FP16 on H100
```
