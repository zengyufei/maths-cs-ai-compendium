    部署与 DevOps¶

    部署是模型不再只是研究制品、而开始成为产品的地方。本节涵盖机器学习场景下的 Docker、模型服务、实验跟踪、可复现性、生产监控、特征存储和管道编排，即把训练好的模型从 notebook 交付给数百万用户所需的基础设施。

    • 只能在你的笔记本上运行的模型是原型；能稳定地大规模运行、在毫秒内提供预测、从故障中恢复且可零停机更新的模型才是产品。两者之间的差距就是部署与 DevOps。

    大白话

    训练出模型只是开始。产品还必须能稳定接请求、扛住流量、出故障能恢复、升级不影响用户。

    • 大多数机器学习工程师花在部署、监控和调试生产问题上的时间，多于训练模型。任何构建真实机器学习系统的人都不能回避理解这些基础设施。

    大白话

    真实工作里，模型效果之外还有环境、依赖、流量、数据和故障，这些往往更耗工程时间。

    面向机器学习的 Docker¶

    • 第 13 章（操作系统）已从概念上介绍容器。这里关注实践：为机器学习工作负载编写 Dockerfile。

    大白话

    Docker 把“程序依赖什么环境”写成可重复构建的配方，换机器时不再靠手动安装。

    • Dockerfile 是构建容器镜像的配方：
    # Start from an official CUDA base image
FROM nvidia/cuda:12.1.0-cudnn8-runtime-ubuntu22.04

# System dependencies
RUN apt-get update && apt-get install -y \
    python3.11 python3-pip git \
    && rm -rf /var/lib/apt/lists/*

# Python dependencies (install separately for caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy source code (changes frequently, so this layer is last)
COPY src/ /app/src/
COPY configs/ /app/configs/
WORKDIR /app

# Entry point
CMD ["python3", "src/scripts/serve.py", "--config", "configs/serve.yaml"]

    大白话

    Dockerfile 从基础镜像开始，装系统依赖和 Python 包，复制项目代码，最后声明启动命令。

    • 层缓存：Docker 会缓存每一层。若 requirements.txt 未变，重建时会跳过 pip install。把不常变的层（系统软件包、pip install）放在常变的层（源代码）之前。这样可将 10 分钟的构建缩短为 10 秒的重建。

    大白话

    Docker 只重做发生变化之后的层，所以把很少变化、构建很慢的依赖放前面，改代码时才能快速重建。

    • GPU 访问：使用 nvidia/cuda 基础镜像，并以 docker run --gpus all 运行。nvidia-container-toolkit 为从主机到容器的 GPU 透传提供支持。

    大白话

    容器默认看不见主机 GPU，必须同时有合适 CUDA 镜像、运行参数和主机工具链。

    • 多阶段构建会通过分离构建环境与运行环境来减小镜像体积：
    # Build stage: install build tools, compile dependencies
FROM python:3.11 AS builder
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# Runtime stage: only runtime dependencies
FROM nvidia/cuda:12.1.0-cudnn8-runtime-ubuntu22.04
COPY --from=builder /root/.local /root/.local
COPY src/ /app/src/
ENV PATH=/root/.local/bin:$PATH

    大白话

    编译需要的工具只留在构建阶段，最终运行镜像只带运行必需品，传输更快、攻击面更小。

    • 最终镜像只包含运行时库，不包含编译器、头文件或构建工具。5 GB 的构建镜像可变为 2 GB 的运行镜像。

    大白话

    生产镜像越小，启动和拉取越快，包含的无关工具也越少。

    • Docker Compose 可运行多容器组合（模型服务器 + 负载均衡器 + 监控）：
    # docker-compose.yml
services:
  model:
    build: .
    ports:
      - "8080:8080"
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]
  prometheus:
    image: prom/prometheus
    ports:
      - "9090:9090"

    大白话

    Compose 用一个文件描述多个互相依赖的服务，适合本地开发和小规模部署环境。

    模型服务¶

    • 模型服务是将推理作为服务运行：接收请求、运行模型、返回预测。

    大白话

    模型服务把一次预测包装成可靠接口，负责接收输入、调模型、返回结果和管理并发。

    • FastAPI（第 03 节介绍）是低至中等吞吐量最简单的方案。对于高吞吐量和 GPU 优化服务，使用专用工具：

    大白话

    请求不多时 FastAPI 足够直接；GPU 高并发场景要交给能批处理和管理模型的专用推理服务器。

    • Triton Inference Server（NVIDIA）：为 TensorRT、ONNX、PyTorch 和 TensorFlow 格式提供服务。特性包括：
      • 动态批处理：收集单个请求并将它们组成批次，从而提高 GPU 效率。单请求流被组合为 32 个一组，可显著提高吞吐量。
      • 模型集成：在单个请求中串联多个模型（预处理器 → 模型 → 后处理器）。
      • 多模型服务：在同一 GPU 上服务多个模型，共享资源。
      • 并发模型执行：在同一 GPU 上并行运行多个推理请求。

    大白话

    Triton 的核心价值是把请求凑批、串模型和多模型调度交给服务器，提高 GPU 利用率。

    • TorchServe（PyTorch）：通过 REST/gRPC API 提供 PyTorch 模型服务。支持模型版本控制、A/B 测试和自定义处理器。

    大白话

    TorchServe 面向 PyTorch 模型提供封装好的服务能力，适合需要版本和灰度试验的团队。

    • vLLM：专为大语言模型服务设计。实现 PagedAttention（高效的 KV 缓存管理）、连续批处理和跨 GPU 张量并行。对大语言模型，其吞吐量可达朴素服务方式的 10 至 20 倍。

    大白话

    LLM 服务的瓶颈常在 KV 缓存和请求调度，vLLM 专门优化这些部分，让不同长度请求也能高效共用 GPU。

    • Cactus（github.com/cactus-compute/cactus）：面向移动端和边缘端设备内服务的低延迟 AI 引擎。Cactus 提供兼容 OpenAI 的 API（聊天补全、流式输出、工具调用、转写、嵌入、RAG、视觉），完全在设备上运行；当本地模型无法处理请求时，自动回退到云端。这种混合架构意味着，无论推理在本地还是云端运行，应用代码使用同一 API，具体由引擎根据模型置信度和设备能力决定。提供 Python、Swift、Kotlin、Flutter、React Native 和 Rust SDK，并在 HuggingFace 提供预转换模型权重。支持多模态推理（LLM、视觉、语音），具有自定义 ARM SIMD 内核以在 ARM CPU 上获得最快推理，以及零拷贝内存映射以实现 10 倍更低的 RAM 使用量（第 16、17 章）。

    • 模型格式优化：

      • ONNX：用于互操作性的开放格式。可从 PyTorch/TensorFlow 导出，随处运行。
      • TensorRT：NVIDIA 的优化器。融合层、选择最优内核、量化权重。在 NVIDIA GPU 上通常比 PyTorch 快 2 至 5 倍。
      • GGUF/GGML：适合 CPU 高效推理的格式，常用于在消费级硬件上运行 LLM。

    大白话

    模型格式决定模型能在哪运行、如何优化。跨框架选 ONNX，NVIDIA GPU 深度优化选 TensorRT，CPU LLM 常见 GGUF。

    实验跟踪¶

    • 没有实验跟踪时，机器学习研究会退化为：“我觉得上周二那个、我改了某个配置的模型最好，但我不记得改了什么。”

    大白话

    不记录实验，模型迭代很快会变成凭记忆猜哪次更好，结论无法复查。

    • Weights & Biases（W&B）：最流行的实验跟踪器。可从训练脚本记录任何内容：
    import wandb

wandb.init(project="my-project", config={
    "model": "transformer",
    "lr": 3e-4,
    "batch_size": 64,
})

for epoch in range(num_epochs):
    train_loss = train_one_epoch()
    val_loss = validate()

    wandb.log({
        "train/loss": train_loss,
        "val/loss": val_loss,
        "epoch": epoch,
    })

    # Log model as artifact
    if val_loss < best_loss:
        wandb.save("best_model.pt")

wandb.finish()
    • W&B 提供：用于比较运行的仪表板、超参数扫描工具、模型注册表、数据集版本控制和团队协作。

    大白话

    实验平台把每次运行的参数、曲线、模型和数据版本集中保存，比较多个实验不再靠散落的日志文件。

    • MLflow：开源替代方案，可在本地或服务器上运行：
    import mlflow

mlflow.set_experiment("my-experiment")

with mlflow.start_run():
    mlflow.log_params({"lr": 3e-4, "batch_size": 64})
    mlflow.log_metric("val_loss", 0.042, step=epoch)
    mlflow.pytorch.log_model(model, "model")
    • 模型注册表：存放已训练模型的中央库，提供版本控制、阶段流转（开发 → 预发布 → 生产）和元数据。W&B 与 MLflow 均提供注册表。注册表回答：“当前生产中运行的是哪个模型、谁训练了它、其验证准确率是多少，以及是哪份代码/数据产出的它？”

    大白话

    模型注册表是生产模型的档案库，能查清哪个版本在服务、它怎么来的、能否安全回滚。

    可复现性¶

    • 可复现性指：给定相同代码、数据和配置，产出同一模型。这在机器学习中出乎意料地困难，因为 GPU 操作、数据打乱和浮点累加都具有非确定性。

    大白话

    即使代码相同，随机顺序和 GPU 数值细节也可能让结果不同，所以复现要控制的东西比想象中多。

    • 可复现性清单：
    内容 方法
    代码版本 Git 提交哈希
    配置 / 超参数 配置文件（在 git 中版本化或记录到 W&B）
    随机种子 设置并记录全部种子（Python、NumPy、PyTorch、CUDA）
    数据版本 DVC 哈希、数据集版本标签或 S3 对象版本
    依赖 pip freeze、Docker 镜像哈希或锁文件
    硬件 GPU 类型、GPU 数量、CUDA 版本
    非确定性 torch.backends.cudnn.deterministic = True（较慢但可复现）

    大白话

    可复现不是只固定一个随机种子，而是把代码、数据、依赖、硬件和配置一起留下证据。

    • 锁定一切版本：使用 pip install torch==2.2.1，而非 torch>=2.0。一个小版本升级即可改变数值行为、优化器实现或默认超参数。

    大白话

    依赖版本的小变化也可能影响训练结果；要复现旧实验，就必须能拿回同一组版本。

    • 使用 Docker 实现可复现性：Docker 镜像锁定操作系统、系统库、Python 版本和 pip 软件包。镜像哈希是完整的环境指纹。能复现 Docker 镜像，就能复现训练。

    大白话

    Docker 把环境也变成可版本化产物，镜像哈希相当于一次训练所用运行环境的身份证。

    生产环境监控¶

    • 部署模型不是终点，而是一组新问题的起点。随着现实世界变化，模型会随时间退化（概念漂移）；输入数据分布变化时也会退化（数据漂移）。

    大白话

    模型上线后现实会变，昨天准确不代表今天还准，所以必须持续观察线上数据和结果。

    • 要监控什么：

      • 延迟：推理耗时多久？跟踪 p50（中位数）、p95 和 p99。p99 为 500ms 表示每 100 位用户中有 1 位等待半秒，这可能不可接受。

      • 吞吐量：每秒处理多少请求？系统能否跟上需求？

      • 错误率：有多少比例的请求失败（异常、超时、无效输入）？

      • 模型指标：留出集上的准确率、精确率和召回率。若生产中存在带标签的数据（例如用户修正），应跟踪在线指标。

      • 数据漂移：传入数据的分布是否发生变化？在日间照片训练的模型，可能在夜间照片上失效。统计检验（KS 检验、PSI）比较训练分布与实时分布。

      • 特征漂移：单个特征分布是否发生变化？一个训练时呈正态分布、现在却呈双峰的特征，提示数据管道存在问题。

    大白话

    既要监控系统是否快和稳定，也要监控模型输入和效果是否变质；只看 CPU/GPU 不能发现模型失效。

    • 工具：
      • Prometheus + Grafana：基础设施监控标准组合。Prometheus 收集指标，Grafana 在仪表板中可视化并发出告警。
      • Evidently AI：开源机器学习监控工具，可生成关于数据漂移、模型性能和数据质量的报告。

    大白话

    Prometheus/Grafana 盯基础设施，Evidently 等工具盯数据和模型行为，两类监控缺一不可。

    • 告警：不要只做仪表板，要配置自动告警。“若 p99 延迟连续 5 分钟超过 200ms，发送 Slack 通知。”“若数据漂移分数超过阈值，呼叫值班工程师。”

    大白话

    仪表板要有人盯才有用；关键阈值必须自动报警，才能在用户先发现问题前处理。

    特征存储¶

    • 特征存储（feature store）是预计算特征的集中式仓库，在训练与服务之间共享。它解决两个问题：

      • 训练-服务偏差：训练时使用的特征必须与服务时使用的完全一致。若训练以一种方式计算 user_age_at_signup，服务时以另一种方式计算，模型预测会悄然出错。

      • 特征复用：多个模型常使用相同特征（用户人口统计、物品嵌入、聚合统计）。计算一次并共享，可避免重复与不一致。

    大白话

    特征存储让训练和线上使用同一份特征定义，避免“训练一套、服务又算出另一套”的静默偏差。

    • Feast 是最受欢迎的开源特征存储。它管理在线特征（低延迟，从 Redis 或 DynamoDB 提供服务）和离线特征（批处理，存储于数据仓库中用于训练）。

    大白话

    在线特征追求毫秒读取，离线特征追求大规模训练查询；特征存储把两者的定义对齐。

    • 特征存储对推荐系统、欺诈检测以及任何从原始数据管道计算特征的应用都至关重要。

    管道编排¶

    • 生产级机器学习系统不只是模型，而是一条管道：数据摄取 → 预处理 → 特征计算 → 训练 → 评估 → 部署 → 监控。每一步依赖前一步、可独立失败，也可能需要按不同计划运行。

    大白话

    生产 ML 是一串依赖步骤，不是一条 train.py；任何一步失败或数据没到，都要能看见和恢复。

    • 编排器管理这些管道：

    大白话

    编排器负责知道步骤依赖、何时运行、失败怎么重试和当前卡在哪，不让人靠手工脚本串流程。

    • Apache Airflow：数据管道编排的标准。DAG（有向无环图）定义任务依赖。每个任务独立运行、失败时可重试，并通过 Web UI 监控。
    # airflow DAG example (simplified)
from airflow import DAG
from airflow.operators.python import PythonOperator

dag = DAG("training_pipeline", schedule="@daily")

preprocess = PythonOperator(task_id="preprocess", python_callable=preprocess_data, dag=dag)
train = PythonOperator(task_id="train", python_callable=train_model, dag=dag)
evaluate = PythonOperator(task_id="evaluate", python_callable=evaluate_model, dag=dag)
deploy = PythonOperator(task_id="deploy", python_callable=deploy_model, dag=dag)

preprocess >> train >> evaluate >> deploy

    大白话

    Airflow 把流程画成 DAG，只有前置任务成功后后置任务才运行，失败可以按任务粒度重试。

    • Kubeflow Pipelines：Kubernetes 上的机器学习专用编排。每步都在容器中运行，按需分配 GPU 资源，实验自动跟踪。

    大白话

    Kubeflow 更贴近容器化 ML 工作负载，能把每一步放进独立容器并按需申请 GPU。

    • Prefect 与 Dagster：Airflow 的现代替代品，具有更好的开发者体验、原生 Python API 和内置数据血缘。

    大白话

    Prefect 和 Dagster 也解决同一类编排问题，偏向更现代的 Python 开发体验和数据血缘可视化。

    • 何时进行编排：当管道超过 2 至 3 步、按计划运行、涉及多个团队或服务，或需要从故障中自动恢复时。单脚本训练任务不需要编排器；每天从 5 个来源摄取数据、训练 3 个模型、评估并部署最佳模型的再训练管道，则绝对需要。

    大白话

    不要给一个一次性脚本上编排平台；当流程长、定时、跨服务或必须自动恢复时，编排才值得它的复杂度。
