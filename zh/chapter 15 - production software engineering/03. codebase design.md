# 代码库设计与模式

*优秀的代码库设计将研究原型与生产软件区分开来。本节涵盖项目结构、整洁代码原则、与机器学习相关的设计模式、配置管理、日志、API 设计和打包。*

- 大多数机器学习代码始于一个 Jupyter notebook。notebook 不断增长、被复制、修改、共享，最终变成由全局变量、废弃单元格和魔法数字构成的、无法维护的纠结体。**代码库设计**是一门将代码组织为可随项目增长而保持可理解、可修改的学科。

- 这不是为了规则本身而遵守规则，而是为了缩短“我想改 X”与“X 已改好且能运行”之间的时间。在设计良好的代码库中，这段时间是几分钟；在糟糕的代码库中，则是数天挖掘没有文档的意大利面代码。

## 项目结构

- 一致的项目布局让任何人（包括未来的你）都能立即定位代码库中的内容。

```
my_project/
├── src/my_project/       # source code (importable package)
│   ├── __init__.py
│   ├── data/             # data loading and preprocessing
│   │   ├── __init__.py
│   │   ├── dataset.py
│   │   └── transforms.py
│   ├── models/           # model architectures
│   │   ├── __init__.py
│   │   ├── transformer.py
│   │   └── layers.py
│   ├── training/         # training loops, optimisers
│   │   ├── __init__.py
│   │   ├── trainer.py
│   │   └── losses.py
│   └── utils/            # shared utilities
│       ├── __init__.py
│       └── logging.py
├── configs/              # configuration files
│   ├── base.yaml
│   └── experiment_1.yaml
├── scripts/              # entry points (train, evaluate, serve)
│   ├── train.py
│   ├── evaluate.py
│   └── serve.py
├── tests/                # test files (mirrors src/ structure)
│   ├── test_dataset.py
│   ├── test_model.py
│   └── test_trainer.py
├── notebooks/            # exploration only (not production code)
├── pyproject.toml        # project metadata and dependencies
├── README.md
├── .gitignore
└── Dockerfile
```

- **`src/` 布局**：将源代码放在 `src/my_project/` 下，可以避免意外从当前目录导入（这会掩盖会在生产环境暴露的导入错误）。开发时使用 `pip install -e .` 安装。

- **单体仓库与多仓库**：**单体仓库（monorepo）**将所有相关项目置于一个仓库（跨项目修改和共享 CI 更方便）。**多仓库（multi-repo）**让每个项目各有仓库（边界更清晰、可独立版本化）。大多数机器学习团队从单体仓库开始，必要时再拆分。

- **脚本与库**：将入口点（`train.py`、`evaluate.py`）保留在 `scripts/`。将可复用逻辑放在 `src/`。训练脚本应约为 50 行：解析配置、构建数据集、构建模型、构建训练器、训练。所有复杂性都应位于库中。

## 整洁代码原则

- **命名**：这是你能做的影响最大的一件事。名为 `x` 的变量要求你阅读上下文才能理解；名为 `learning_rate` 的变量则自带说明。

```python
# BAD
def proc(d, n, lr):
    for i in range(n):
        for k, v in d.items():
            v -= lr * g[k]

# GOOD
def update_parameters(parameters, num_steps, learning_rate):
    for step in range(num_steps):
        for name, param in parameters.items():
            param -= learning_rate * gradients[name]
```

- **单一职责原则**：每个函数或类只做一件事。名为 `load_data_and_train_model` 的函数做了两件事，应当拆分。这使每个部分都能独立测试、复用和理解。

- **DRY（Don't Repeat Yourself，避免重复）**，但不要过早套用。若一段代码复制粘贴了三次，就提取为函数；但不要为只用过一次的代码创建抽象。过早抽象比重复更糟：它增加复杂性，却没有经过验证的收益。

```python
# Premature abstraction (one use case, over-engineered)
class AbstractDataTransformPipelineFactory:
    ...

# Just right (direct, clear, used in three places)
def normalise_image(image, mean, std):
    return (image - mean) / std
```

- **魔法数字**：绝不要使用未经说明的字面值。

```python
# BAD
if len(batch) > 32:
    split_batch(batch, 32)

# GOOD
MAX_BATCH_SIZE = 32
if len(batch) > MAX_BATCH_SIZE:
    split_batch(batch, MAX_BATCH_SIZE)
```

- **函数应保持短小**：若一个函数放不进一屏（约 30 行），它很可能做得太多。将逻辑片段提取为名称具有描述性的辅助函数。函数体随后就像一份高层摘要。

## 面向机器学习的设计模式

- 设计模式是常见问题的可复用解决方案。以下模式最适合机器学习代码库：

- **工厂模式**：创建对象时不指定确切类。当配置写着 `model: "transformer"`、而你需要实例化正确的类时，它很有用：

```python
MODEL_REGISTRY = {
    "transformer": TransformerModel,
    "cnn": CNNModel,
    "mlp": MLPModel,
}

def build_model(config):
    model_cls = MODEL_REGISTRY[config["model"]]
    return model_cls(**config["model_params"])
```

- 这会将训练脚本与具体模型实现解耦。添加新模型意味着在注册表添加一行，而不是修改训练循环。

- **策略模式**：在运行时交换算法。适用于损失函数、优化器和调度器：

```python
LOSS_FUNCTIONS = {
    "mse": nn.MSELoss,
    "cross_entropy": nn.CrossEntropyLoss,
    "focal": FocalLoss,
}

loss_fn = LOSS_FUNCTIONS[config["loss"]]()
```

- **观察者模式**（回调/钩子）：让模块在不紧耦合的前提下对事件作出反应。训练框架（PyTorch Lightning、Keras）广泛使用回调：

```python
class EarlyStopping:
    def __init__(self, patience=5):
        self.patience = patience
        self.best_loss = float('inf')
        self.counter = 0

    def on_epoch_end(self, epoch, val_loss):
        if val_loss < self.best_loss:
            self.best_loss = val_loss
            self.counter = 0
        else:
            self.counter += 1
            if self.counter >= self.patience:
                return "stop"
```

- **依赖注入**：将依赖传入函数或类，而非在其中创建。这使测试更简单（可注入 mock），配置也更灵活：

```python
# BAD: hard-coded dependency
class Trainer:
    def __init__(self):
        self.logger = WandbLogger()  # cannot test without W&B

# GOOD: injected dependency
class Trainer:
    def __init__(self, logger):
        self.logger = logger  # can inject any logger, including a mock
```

## 配置管理

- 对超参数、文件路径和模型设置进行硬编码，会使实验不可复现、修改困难。应将**配置外置**到文件中。

- **YAML** 是机器学习配置最常见的格式：

```yaml
# configs/experiment_1.yaml
model:
  name: transformer
  d_model: 512
  n_heads: 8
  n_layers: 6

training:
  batch_size: 64
  learning_rate: 3e-4
  max_epochs: 100
  early_stopping_patience: 10

data:
  train_path: /data/train.parquet
  val_path: /data/val.parquet
  max_seq_length: 512
```

- **Hydra**（Facebook）是一个配置框架，支持组合（将基础配置与实验专用覆盖项合并）、命令行覆盖（`python train.py training.lr=1e-3`）和多次运行（扫描超参数）。

- 对参数较少的脚本，**argparse** 更简单：

```python
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--lr", type=float, default=3e-4)
parser.add_argument("--batch-size", type=int, default=64)
parser.add_argument("--config", type=str, default="configs/base.yaml")
args = parser.parse_args()
```

- **最佳实践**：准备包含全部默认值的基础配置，再准备每个实验的配置，只覆盖变化项。将每个实验的配置与结果一同跟踪。

## 日志与可观测性

- `print` 语句用于调试。**日志**用于生产：

```python
import logging

logger = logging.getLogger(__name__)
logger.setLevel(logging.INFO)

logger.debug("Batch loaded: %d samples", len(batch))     # noisy, for debugging
logger.info("Epoch %d: loss=%.4f, lr=%.6f", epoch, loss, lr)  # normal operation
logger.warning("GPU memory >90%%, consider reducing batch size")
logger.error("Failed to load checkpoint: %s", path)       # recoverable error
logger.critical("CUDA out of memory, aborting")            # fatal
```

- **为何不用 print**：日志支持级别（在生产中过滤调试消息）、格式化（时间戳、模块名）和处理器（写入文件、发送至监控系统），且无需修改日志调用点。

- **结构化日志**会在面向人的消息之外输出机器可解析格式（JSON）。这样可以针对特定字段搜索和告警：

```python
logger.info("training_step", extra={
    "epoch": 5, "step": 1200, "loss": 0.0342, "lr": 2.1e-4
})
```

## API 设计

- 若其他服务（Web 应用、移动应用、另一条机器学习管道）要使用你的模型，它就需要一个 **API**（应用程序编程接口）。

- **REST API** 使用 HTTP 方法：`GET` 用于读取，`POST` 用于创建或预测，`PUT` 用于更新，`DELETE` 用于删除。端点遵循以资源为中心的命名：

```
POST /api/v1/predict          # send input, get prediction
GET  /api/v1/models           # list available models
GET  /api/v1/models/{id}      # get model details
POST /api/v1/models/{id}/predict  # predict with a specific model
```

- **FastAPI** 是机器学习服务的首选 Python 框架：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class PredictRequest(BaseModel):
    text: str

class PredictResponse(BaseModel):
    label: str
    confidence: float

@app.post("/predict", response_model=PredictResponse)
async def predict(request: PredictRequest):
    result = model.predict(request.text)
    return PredictResponse(label=result.label, confidence=result.score)
```

- FastAPI 会自动生成 API 文档（`/docs` 上的 Swagger UI），使用 Pydantic 模型验证输入与输出，并支持异步以获得高吞吐量。

- **gRPC** 对内部服务间通信比 REST 更快。它使用 Protocol Buffers（二进制序列化，比 JSON 更小、更快）并支持流式传输。TensorFlow Serving、Triton Inference Server 和许多微服务架构都在使用它。

## 打包与分发

- 将代码制作为可安装包，能让他人（以及你自己的脚本）干净地导入它：

```toml
# pyproject.toml
[project]
name = "my-ml-project"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = [
    "torch>=2.0",
    "jax>=0.4",
    "pydantic>=2.0",
]

[project.optional-dependencies]
dev = ["pytest", "ruff", "mypy"]

[build-system]
requires = ["setuptools>=64"]
build-backend = "setuptools.backends._legacy:_Backend"
```

```bash
pip install -e ".[dev]"    # install in editable mode with dev dependencies
```

- **可编辑安装**（`-e`）：源代码的改动无需重新安装就会立即生效。这在开发期间不可或缺。

- **锁定依赖版本**：在 `requirements.txt` 中使用精确版本（`torch==2.2.1`，而非 `torch>=2.0`）可确保可复现性。使用 `pip freeze > requirements.txt` 捕获当前环境。若需更成熟的依赖管理，可使用 `uv`、`poetry` 或 `pip-tools`。

## 与 AI 编程代理协作

- AI 编程代理（Claude Code、GitHub Copilot、Cursor 等）如今已是专业工程工作流的一部分。用得好会显著加速开发；用得差则会引入隐蔽缺陷、侵蚀你对自身代码库的理解，并制造虚假的生产力感。

- 正确的心智模型是：**代理是一位速度快但经验不足的结对程序员**。它写代码很快，熟悉语法和标准模式，读过的文档也比你一生能读的更多。但它不了解你的具体系统、业务约束、边界情形，也不了解设计决策背后的*原因*。你是高级工程师，代理是初级工程师；你负责指导、审查并承担责任。

### 代理擅长的场景

- **样板与脚手架**：生成 Dockerfile、CI 配置、测试夹具、数据类定义和 argparse 设置。这些遵循公认模式，手写繁琐。可让代理生成，再审查其正确性。

- **编写测试**：描述函数行为，代理即可生成测试用例。它常能发现你遗漏的边界情形（空输入、负值、Unicode）。始终阅读生成的测试：它们检验的是你的假设，而不仅是代码。

- **重构**：例如“把此块提取为函数”、“将此类改为使用 dataclass”、“为该模块增加类型标注”。这些是意图明确、细微错误风险较低的机械转换。

- **探索与原型**：例如“写个快速脚本测量推理延迟”或“展示如何使用 HuggingFace 词元化器 API”。代理比阅读文档更快地提供可工作的起点。

- **文档与文档字符串**：代理可根据代码结构生成文档。需要审查准确性，但繁琐劳动可自动化。

- **调试辅助**：贴入错误回溯并请求诊断。代理常能定位根因并建议修复，尤其针对常见问题（形状不匹配、导入错误、CUDA 显存不足）。

### 不应依赖代理的场景

- **新颖架构决策**：若你正在设计新的训练管道，代理只会给出通用答案。它不了解数据约束、延迟要求或团队专长。请使用代理实现你已经思考清楚的设计。

- **安全关键代码**：认证、加密、输入净化。代理可能生成看似正确、实则有微妙漏洞的代码（SQL 注入、不安全默认值、时序攻击）。安全代码应由理解威胁模型的人编写，并由他人审查。

- **性能关键的内层循环**：代理会写出正确但朴素的代码。对于 GPU 内核、内存关键数据结构或延迟敏感的服务路径，你必须理解硬件约束（第 13、16 章）并有意识地优化。

- **你不理解的代码**：若代理生成 200 行代码而你无法解释每一行，就不要提交。你正在维护不理解的代码；当它出错时（它会出错），你无法调试。这是最常见也最危险的失败模式。

### 审查纪律

- 提交前**始终阅读生成代码的每一行**。这不是可选项。代理的代码是草稿，不是完成品。像审查同事提交的拉取请求一样严格审查它。

- **检查内容**：
    - **正确性**：它是否真的完成了你的要求？代理常会解决一个与你意图略有不同的问题。
    - **边界情形**：它是否处理空输入、None 值、负数和极大输入？代理常常遗漏边界处理。
    - **幻觉 API**：代理可能调用不存在的函数或参数，尤其针对较新或不常见的库。验证每个 API 调用真实存在。
    - **过度工程**：代理往往生成超过必要数量的代码。用 50 行解决 10 行的问题会平白增加复杂性。要果断简化。
    - **安全性**：硬编码密钥、未净化的用户输入、不安全默认值。代理不会从对抗视角思考。
    - **风格一致性**：生成代码是否符合项目约定（命名、模式、错误处理）？

### 如何编写好的提示词

- 代理输出的质量与指令质量成正比。模糊提示会得到模糊代码。

- **差**："编写一个数据加载器"
- **好**："为带有 'text' 和 'label' 列的 CSV 文件编写 PyTorch DataLoader。使用 HuggingFace 词元化器 'bert-base-uncased' 将文本词元化，max_length=512。返回张量 input_ids、attention_mask 和 label。若 CSV 的 label 列含有缺失值，则跳过这些行。"

- **提供上下文**：告知代理项目结构、现有代码、约束与约定。上下文越多，输出越好。

- **明确约束**：例如“仅用标准库”、“必须兼容 Python 3.10”、“不要使用全局变量”、“遵循 `src/models/transformer.py` 中的现有模式”。

- **要求解释**：例如“实现 X 并解释关键设计决策”。这迫使代理表达推理，让你更容易发现错误假设。

### 使用质量关卡捕获代理错误

- 你已有的质量基础设施（第 04 节）对代理和人类错误同样有效：

    - **类型检查（mypy）**：捕获虚构 API 签名和类型不匹配。
    - **静态检查（ruff）**：捕获未使用导入、未定义变量和风格违规。
    - **测试（pytest）**：若代理代码通过测试套件，则更可能正确。若没有测试，应在请求代理实现功能*之前*编写它们（测试驱动开发尤其适合与代理协作）。
    - **CI 管道**：每次提交时自动运行上述全部检查。

- “代理编写代码” + “质量关卡验证代码”的组合，比单独使用任何一方都更高效。代理快但粗心；质量关卡彻底却不写代码。二者结合可同时获得速度和正确性。

### 生产力陷阱

- 编程代理最大的风险是**生产力幻觉**。你可以在 10 分钟内生成 500 行代码；但若因不理解它们而花两小时调试这 500 行，你还不如自己在 30 分钟内写完 200 行。

- 与代理协作的真实生产力来自：
    1. **保持控制权**：你决定架构，代理填入实现。
    2. **理解生成内容**：若无法解释，就重写它或要求代理简化。
    3. **投入质量关卡**：测试、类型和静态检查会在每次代理交互中摊薄其成本。
    4. **将代理用于你的弱项**：若你擅长算法却写测试慢，让代理写测试；若你擅长 UI 代码却不熟数据库查询，让代理起草 SQL。发挥你的强项，委托你的缺口。

- 最能从编程代理获益的工程师，正是已经懂得如何写好代码的人。代理放大既有技能，不能替代它。理解数据结构、算法、系统设计和软件工程（本章全部内容），才能让你有效指导代理并严格评估其输出。
