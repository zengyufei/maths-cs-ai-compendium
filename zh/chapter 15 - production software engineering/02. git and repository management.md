# Git 与版本控制

*Git 让软件团队能够协作而不会互相覆盖工作。本节涵盖 Git 的心智模型、分支策略、合并与变基、冲突解决、拉取请求，以及大文件和实验跟踪等机器学习特有挑战的管理方式。*

- 每个严肃的软件项目都使用版本控制。**Git** 是占据主导地位的系统，几乎所有开源项目和公司都在使用它。没有 git，协作就是互发 zip 文件并祈祷没人覆盖你的改动。有了 git，每项改动都有记录、可回退且可追溯责任。

!!! note "大白话"
    Git 是代码的时间机器和协作账本：谁改了什么、何时改的、能不能撤回，都有记录。

- 对机器学习工程师而言：git 跟踪代码、配置和实验脚本。它与实验跟踪工具结合后可实现可复现性："究竟是哪一版代码和配置产出了这个模型？"

!!! note "大白话"
    模型结果离不开代码和配置版本；不记录它们，复现一个好结果时只能靠猜。

## 心智模型

- Git 跟踪项目的**快照**。每次提交都是该时刻所有已跟踪文件的完整快照，而不是差异（git 内部会为效率存储差异，但从概念上看，每次提交都是完整状态）。

!!! note "大白话"
    可以把提交理解为某一刻项目的完整存档，切换提交就是把项目恢复到那个存档状态。

- 文件存在四个“位置”：

    1. **工作目录**：磁盘上的实际文件。你在这里编辑。
    2. **暂存区**（index）：已标记为将在下一次提交中包含的文件。`git add` 将改动移到这里。
    3. **本地仓库**：提交历史，存储在 `.git/` 中。`git commit` 将暂存区保存为新快照。
    4. **远程仓库**（例如 GitHub）：共享副本。`git push` 上传你的提交，`git pull` 下载其他人的提交。

```
Working Dir  →  git add  →  Staging  →  git commit  →  Local Repo  →  git push  →  Remote
                                                        ←  git pull  ←
```

!!! note "大白话"
    文件先在工作区修改，再挑选进暂存区，提交到本地历史，最后推送到远程共享仓库。

- 暂存区是 git 强大的原因。你可以编辑 10 个文件，却只提交其中 3 个，将其余改动留给另一次提交。这使提交能保持干净且聚焦。

!!! note "大白话"
    暂存区像结账篮子，今天改了很多东西，也可以只把同一件事相关的改动放进这次提交。

### 核心命令

```bash
git init                          # create a new repository
git clone url                     # download a remote repository
git status                        # what has changed? (most-used command)
git add file.py                   # stage a specific file
git add .                         # stage all changes (use with caution)
git commit -m "descriptive msg"   # commit staged changes
git push                          # upload commits to remote
git pull                          # download + merge remote changes
git log --oneline                 # compact commit history
git diff                          # show unstaged changes
git diff --staged                 # show staged changes
```

## 分支

- **分支**是指向某次提交的指针。默认分支是 `main`（或 `master`）。创建分支会得到一条独立开发线：你可以修改而不影响 `main`。

!!! note "大白话"
    分支是从某个项目快照岔出去的工作线，实验和修复可以在上面进行，不影响稳定主线。

```bash
git branch feature-x              # create a branch
git checkout feature-x            # switch to it
git checkout -b feature-x         # create and switch in one step
git branch -d feature-x           # delete branch (after merging)
git branch -a                     # list all branches (local + remote)
```

- **何时创建分支**：始终如此。不要直接向 `main` 提交。每个功能、缺陷修复或实验都应有自己的分支。这让 `main` 保持稳定、可部署。

!!! note "大白话"
    把 `main` 当成随时可发布的主干；日常改动放分支，检查通过再合回来。

### 分支策略

- **功能分支**（最常见）：每项功能或修复都从 `main` 切出一个分支。完成后，发起拉取请求（PR）合并回去。简单，适用于大多数团队。

!!! note "大白话"
    功能分支最直白：一项任务一条短分支，做完经审查后合并，适合多数团队。

- **主干开发**：开发者频繁向 `main` 提交（每天多次），用功能开关隐藏未完成的工作。持续部署的团队（Google、Facebook）偏好此模式。它要求出色的 CI/CD。

!!! note "大白话"
    主干开发要求所有人频繁、小步地合入主线，未完成功能靠开关隐藏，对自动测试和发布纪律要求很高。

- **Gitflow**：为功能、发布和紧急修复设置不同分支。它更复杂，适合有版本化发布的软件（移动应用、打包软件）。对大多数机器学习项目属于过度配置。

!!! note "大白话"
    Gitflow 分支规则很全，但流程重；没有频繁版本发布需求的 ML 项目通常不值得承担这套复杂度。

- 对机器学习团队来说：使用生命周期短的**功能分支**（1 至 3 天内合并）是最佳平衡点。长期存活的分支会与 `main` 分叉，产生痛苦的合并冲突。

!!! note "大白话"
    分支越久不合，和主线差异越大，冲突越难解；短分支能把风险压小。

## 合并与变基

- **合并**会创建一个新的“合并提交”，将两个分支结合：

```bash
git checkout main
git merge feature-x
```

- 这会保留完整历史：你能看到工作在哪个分支上发生、何时合并。合并提交有两个父提交。

!!! note "大白话"
    merge 把两条历史真正接起来，保留“这批工作从哪条分支来”的信息。

- **变基**会将你的分支提交重放到目标分支顶部：

```bash
git checkout feature-x
git rebase main
```

- 这会重写历史：分支中的提交会得到新的哈希，就像你从当前 `main` 顶端开始工作一样。结果是线性历史（没有合并提交），阅读更清晰。

!!! note "大白话"
    rebase 把你的提交搬到新主线后面，历史更直，但提交身份会变，不能随便对共享历史做。

- **何时使用哪一种**：
    - 使用**变基**以最新 `main` 改动更新功能分支（保持分支整洁且最新）。
    - 使用**合并**将功能分支整合到 `main`（保留分支历史）。
    - **绝不要对已推送并被他人共享的提交变基**。变基会重写历史；若有人基于原提交继续开发，变基会造成混乱。

!!! note "大白话"
    自己独占的分支可以 rebase 保持整洁；真正合入主线时通常 merge。共享提交重写历史会让别人同步时很痛苦。

## 解决冲突

- 当两个分支修改同一文件的同一行时会发生**冲突**。Git 无法自动判定要保留哪个改动，因此要求你手动解决。

```
<<<<<<< HEAD
learning_rate = 0.001
=======
learning_rate = 0.0005
>>>>>>> feature-x
```

!!! note "大白话"
    冲突不是 Git 坏了，而是两个改动都碰到同一位置，需要人根据业务意图决定最终代码。

- `<<<<<<< HEAD` 与 `=======` 之间是当前分支版本。`=======` 与 `>>>>>>> feature-x` 之间是传入分支版本。你决定保留哪一个（或将两者合并），删除标记，保存，然后对已解决的文件执行 `git add`。

!!! note "大白话"
    冲突标记把两个版本摊开给你看；解决后必须删掉标记并重新暂存，Git 才知道这部分已处理。

- **陷阱**：不要将冲突标记留在已提交的文件中。它们是会破坏代码的字面文本。解决后始终搜索 `<<<<<<<`。

!!! note "大白话"
    冲突标记不是注释，留进代码会直接造成语法错误或错误内容，提交前必须搜索确认。

- **减少冲突**：保持分支短命，频繁将 `main` 合并到自己的分支，避免多人同时编辑同一文件。

!!! note "大白话"
    冲突最好的解决方法是少制造它：小步合并、频繁同步、提前划分文件责任。

## 编写好的提交消息

- 提交消息是写给未来的自己和队友看的。"修复缺陷" 没有任何信息。"修复批大小计算的差一错误，该错误会导致 8-GPU 训练 OOM" 则说明了一切。

!!! note "大白话"
    好提交消息要说清问题和影响，未来排查时不用靠翻一大段 diff 猜当时改了什么。

- **格式**：

```
Short summary (50 chars or less, imperative mood)

Longer description if needed. Explain WHY, not WHAT
(the diff shows what changed). Wrap at 72 characters.

Fixes #123
```

- **祈使语气**：写 "Add feature"，不要写 "Added feature" 或 "Adds feature"。把它读作补全一句话：“如果应用此提交，该提交将**添加功能**。”

!!! note "大白话"
    用祈使句是为了让提交历史读起来像一串明确的变更指令，团队风格统一即可。

- **原子提交**：每次提交应只做一件事。“新增数据加载器” 是一次提交。“新增数据加载器、修复无关缺陷并更新 README” 应拆为三次提交。这让 `git bisect`（定位引入缺陷的提交）成为可能。

!!! note "大白话"
    一个提交只承担一个目的，回滚、审查和定位缺陷都会简单得多。

## 拉取请求与代码审查

- **拉取请求（PR）**提议将一个分支合并到 `main`。它是代码审查的关口：队友阅读你的改动、提出改进建议，并在合并前批准。

!!! note "大白话"
    PR 不是形式流程，它是把分支改动公开出来，让别人检查设计、风险和测试证据的地方。

- **优秀 PR 实践**：
    - 保持 PR 小（改动少于 400 行）。大型 PR 往往被走过场批准，因为没人愿意审查 2000 行。
    - 写清楚描述：改了什么、为何修改、如何测试。
    - 链接引发该改动的议题或工单。
    - 及时回复审查评论。
    - 合并前压缩琐碎提交（使 `main` 保持干净历史）。

!!! note "大白话"
    PR 越小、背景和测试越清楚，审查越认真；巨型 PR 往往没人真正能看透。

- **代码审查并非只为找缺陷**（测试负责这一点）。它也用于：知识共享（审查者了解代码库）、设计反馈（这是正确方案吗？）和维持标准（命名、风格、架构）。

!!! note "大白话"
    测试发现程序行为问题，审查还负责让团队共享理解，并阻止架构和维护性逐渐变差。

## .gitignore

- `.gitignore` 文件告诉 git 哪些文件不应被跟踪。对机器学习项目而言：

```gitignore
# Python
__pycache__/
*.pyc
*.egg-info/
.venv/
env/

# Data and models (too large for git)
data/
*.csv
*.parquet
models/
*.pt
*.onnx
*.bin
checkpoints/

# Secrets
.env
*.pem
credentials.json

# IDE
.vscode/
.idea/
*.swp

# OS
.DS_Store
Thumbs.db

# Jupyter
.ipynb_checkpoints/

# Experiment outputs
wandb/
mlruns/
outputs/
logs/
```

!!! note "大白话"
    源码、配置模板应进 Git；大数据、模型、缓存、日志和密钥不该进，因为它们要么太大、要么可再生、要么敏感。

- **陷阱**：在文件已提交后将它加入 `.gitignore`，并不会从仓库中移除它。还必须执行 `git rm --cached file` 以取消跟踪。除非重写历史（很麻烦），否则文件会永远保留在历史中。

!!! note "大白话"
    `.gitignore` 只影响尚未跟踪的文件。机密一旦提交过，即使后来忽略，历史里仍可能泄漏。

## 面向机器学习的 Git

- 机器学习带来了传统软件没有的挑战：

!!! note "大白话"
    ML 项目除了代码，还面对超大数据、模型权重和实验上下文，不能照搬纯代码仓库的管理方式。

- **大文件**：数据集和模型权重可能有数 GB 甚至更大。Git 面向文本文件（源代码）设计，不适合二进制大对象。解决方案：
    - **Git LFS**（Large File Storage）：在 git 中跟踪指针，实际文件存储在单独的服务器上。简单，但 GitHub 上有存储和带宽限制。
    - **DVC**（Data Version Control）：使用远程存储（S3、GCS）管理独立于 git 的数据和模型文件。它像 git 一样管理数据：`dvc add data.csv`、`dvc push`、`dvc pull`。

!!! note "大白话"
    Git 管代码版本，LFS 或 DVC 管大文件内容；不要把数 GB 模型直接塞进普通 Git 提交。

- **实验跟踪**：哪个提交 + 哪组超参数 + 哪份数据产出了哪些指标？Git 跟踪代码，但不会记录完整的实验上下文。
    - **Weights & Biases（W&B）**：记录指标、超参数、系统信息，并关联 git 提交。提供用于比较运行的仪表板。
    - **MLflow**：带模型注册表的开源实验跟踪工具。记录参数、指标和制品。
    - **简单方案**：在训练脚本中记录 git 哈希：`git_hash = subprocess.check_output(['git', 'rev-parse', 'HEAD']).strip()`。将它与结果一同保存。

!!! note "大白话"
    Git 哈希只能回答代码版本，实验系统还要记参数、数据、指标和硬件，才能真正比较和复现结果。

- **可复现性清单**（每次实验应跟踪什么）：
    - Git 提交哈希（精确代码版本）
    - 配置文件 / 超参数
    - 随机种子
    - Python 和库版本（`pip freeze`）
    - 数据版本（DVC 哈希或数据集版本标签）
    - 硬件（GPU 类型、GPU 数量）

!!! note "大白话"
    能复现实验的不是一个模型文件，而是一整套证据：代码、数据、参数、随机性、依赖和硬件。

```bash
# Quick reproducibility snapshot
echo "Commit: $(git rev-parse HEAD)" > experiment_info.txt
echo "Branch: $(git branch --show-current)" >> experiment_info.txt
echo "Dirty: $(git status --porcelain | wc -l) files" >> experiment_info.txt
pip freeze >> experiment_info.txt
nvidia-smi >> experiment_info.txt
```
